# Legacy Player Implementation and Specification Audit

**Audit date:** 2026-08-20  
**Scope:** Current working tree, project handoff, ecosystem rules, automated tests, runtime/server, Dolphin adapter, memory tooling, replay, and documentation  
**Disposition:** Not ready for Tier-0, replay-verification, deterministic multiplayer, or canonical platform claims

## Executive result

The repository has a useful observation toolkit and a tested coordination prototype, but it is not yet the product defined by the handoff. The highest-priority path is correctly identified: behaviorally prove authoritative MEM1 before grounding fields or deriving events.

The automatic suite is green, but several tested components validate internal mechanics rather than the external claims required for release. The current ecosystem identity also remains unclassified.

## Findings

### LP-AUD-001 — Critical: project role is not canonically classified

The ecosystem contract declares the service unclassified with no approved ownership boundary, while the README and handoff assign adapter, game-state, replay, and multiplayer responsibilities. This blocks canonical role claims.

Action: review `docs/proposals/0001_CLASSIFY_LEGACY_PLAYER.md`; update service map, registry, project contract, integration document, tests, and receipt only after approval.

### LP-AUD-002 — Critical: authoritative MEM1 is not proven

`find_dolphin_ram_region` statically selects the first plausible exact mapped nonzero 32 MiB region. The handoff records multiple equal candidates and prior zero-change captures from the wrong region. Geometry and a nonzero prefix do not prove emulated-memory authority.

Impact: every downstream field, event, replay, state-hash, and synchronization claim may be bound to the wrong memory.

Action: complete WBS 6, fail ambiguity, and verify repeatability after restart/reload.

### LP-AUD-003 — High: live identity and DSU evidence can false-pass

Game ID is extracted from visible window-title text; region is inferred from one character. RAM is selected heuristically. The live gate accepts the existence of any unauthenticated DSU subscriber without correlating it to the selected Dolphin process.

Impact: the gate can claim an exact supported game and actual Dolphin registration without proving either.

Action: bind game identity to media/revision evidence, bind RAM to a verified resolution receipt, and correlate adapter evidence with the selected process/session.

### LP-AUD-004 — High: session compatibility validates equality, not support

The session model checks only that participants supplied equal `game_id` and `region` values. It does not verify that the game profile, adapter, game pack, revision, or emulator version is supported or even exists.

Reproduction: a session reached `ready-barrier` with `adapter_id` and `game_pack_id` both set to `does-not-exist`.

Action: load and independently verify adapter/game-pack manifests before validation succeeds.

### LP-AUD-005 — High: replay exhaustion causes irreversible partial finalization

Session completion mutates the session to `completed` before recording the completion event. `ReplayRecorder.record` raises when its event limit is reached. That exception bypasses replay finalization and secret removal, while the completed state prevents retry.

Reproduction with a reduced event limit produced: state `completed`, replay not finalized, host credential retained.

Action: reserve capacity or stage/finalize transactionally; catch storage/limit failures; test every mutating operation at resource boundaries.

### LP-AUD-006 — Critical: restore trusts an arbitrary manifest target

The Dolphin restore operation reads an absolute target path from a user-selected backup directory. A crafted manifest can overwrite a user-writable file or delete it when `original_existed` is false.

Action: bind restore to an approved Dolphin configuration root and fixed target name, validate backup provenance, and refuse to overwrite a target changed since installation without explicit recovery handling.

### LP-AUD-007 — High: incomplete bundles mutate controller state before rejection

The DSU bridge updates and broadcasts each supplied input before checking that all participants are present. A malformed incomplete bundle can therefore cause observable partial input and then fail.

Action: parse and validate the complete bundle into an immutable staging object before any pad update or broadcast.

### LP-AUD-008 — High: replay is recorder-authored evidence without an independent verifier

The replay store atomically replaces a JSON file, but no package digest, canonical byte definition, read-back verification, independent count/hash recomputation, or corruption verifier exists.

Action: implement LP-FR-040 through LP-FR-044 and the replay Definition of Done.

### LP-AUD-009 — Medium: release validation is primarily syntactic

Repository validation parses JSON, checks that Markdown is nonempty, and checks for one supported-profile entry. It does not validate schemas, cross-file references, evidence digests, adapter/pack compatibility, canonical formatting, or claim status.

Action: add semantic schema validators, traceability checks, proof-reference integrity, and clean-checkout enforcement.

### LP-AUD-010 — Medium: documentation mixes targets, prototypes, and proven behavior

Older specs describe intended runtime responsibilities while current code implements only subsets. The README also says Dolphin controller injection is unavailable while a DSU bridge exists; the important limitation is deterministic frame control, not all controller delivery.

Action: use the status vocabulary and documentation index introduced by this documentation set; revise older claims in a separate bounded cleanup.

## Required remediation order

1. Approve or reject the proposed service classification.
2. Fix local destructive restore and replay partial-finalization defects.
3. Implement behavioral MEM1 validation and independent receipt verification.
4. Bind identity to emulator/game revision evidence.
5. Rebuild the discovery corpus against verified MEM1.
6. Ground the five priority board-state fields.
7. Define normalized-state canonical bytes and hashes.
8. Derive semantic events from state and phase.
9. Build independent replay verification.
10. Only then resume deterministic multiplayer and recovery claims.

## Audit conclusion

The architecture is promising and the recent correction toward state-first semantics is sound. The project should be treated as an active research/implementation prototype until authoritative memory, grounded state, independently verified replay, and governance classification are complete.
